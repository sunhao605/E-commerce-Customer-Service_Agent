# CANCEL-ROUTE-003 / 003B：从取消分类到按原因分流

2026-10-11。真实Jev/DeepSeek API；取消、政策、任务及按钮均为隔离Mock，未访问商城或MySQL。原始失败和执行器保留。

用户认可对象澄清、条件补事实、低可靠判断DeepSeek复核、冲突按钮、复合请求拆任务。三个旧案例不是都应澄清：N10“不过现在继续退”应keep；N18需核实运费条件；A05需确认订单/售后对象。001简单明确不取消20次均正确，只能说明那些表达；N10已反证更复杂的明确继续也一定正确。

## 机制

- 保留002B三个Jev问题，以0.85作候选门槛。明确继续只看决定/额外任务，不要求无须取消的对象也高分。
- DeepSeek独立读取原话/必要状态，不看Jev答案。temperature=0、非思考、JSON、max_tokens=512，容纳任务列表；不是证明模型成本更低。
- 对象分数不足或非当前对象必须问清，不能凭两个模型猜测一致跳过。先处理条件/犹豫，再处理对象。
- 条件待核实输出只读政策查询；成功展示事实再等待选择，无结果/故障保留草稿。自付/商家承担仅是注入的Mock事实。
- 冲突/无效复核生成绑定订单与草稿token的保留/取消按钮。复合确认保留任务及顺序，明确点击后执行；准备新退款只准备，不提交。
- Mock任务按序执行；取消失败不继续，后续失败保留已取消事实。不声称全部完成。
- 本人、有效、未提交仍由代码校验。错对象、旧token和重复点击有Mock断言，不是新增Java实际凭证验收。

代码：[当前执行器](run_routing.py)、[初版执行器](run_routing-before.py)。变化是实验控制代码与复核Prompt，不是新增取消关键词；商城业务和Prompt未改。

修正版在初版结果后，修正对象、犹豫优先级、确认保留任务，并明确复核decision只判断当前售后，不被另一个任务覆盖。门槛0.85不变。另12条在调用前冻结，看到输出后没有继续改指令或标签；改动同时涉及代码与Prompt，不能分离各自贡献。

旧三例重放：A05问对象、N10展示保留/取消按钮、N18查询运费事实，各两次不再自动取消。N10标签仍应keep；两模型冲突时执行等待选择，不把原标签改成clarify。

5组冲突按钮的离线点击检查通过，覆盖保留、明确取消、对象/token、顺序、旧/重复凭证，见 [按钮检查](revised/button-check.json)。新12条没有自然触发冲突按钮，因此该分支仅由旧回复重放与Mock检查验证。自检覆盖权限、已提交/无草稿、取消失败停止任务、后续失败保留部分成功；业务/旧冻结哈希未变，密钥扫描通过。
