## 产品设计方向修订：统一业务能力查询，直接呈现可信结果

**用户确认的工作方法：先确定正确产品方向，再确定MVP范围；实现时继续避免不必要复杂度。** 本轮用户提出通过接口查询功能是否支持，比逐功能补一条“必答说明”更合理。助手接受该方向。该方向已按 MVP 落地，接口字段沿 Java 现有驼峰风格，验收见[业务能力查询结果](../../07-不支持业务与人工入口/业务能力查询MVP实现验收/结果.md)。下面的示例 JSON 仍是当时提案，以结果和代码为准。日常服务尚未加载。

### 产品目标与分工

客户问“能不能提醒”“能不能换货”时，业务代码或服务提供当前渠道的可信支持结论，模型负责理解问法和组织其他答复。已识别为能力咨询时，代码确保取得查询结果，不能只让模型自由决定是否调用，导致漏查。

处理路径：识别客户询问的能力与其他问题 → 查询统一业务能力来源 → 分别形成能力查询结果和商品／政策事实 → 呈现所有问题的结果。单纯能力咨询可以直接呈现查询结果；混合咨询继续查价格／库存、解释政策或处理原流程，不能因一项不支持而停止全部回答。

### 能力来源与查询契约

建议让拥有业务实现和开关的电商后端维护一份业务能力目录。MVP用版本化配置及代码映射即可，不增加数据库、管理台或独立微服务；商城与Python读取同一来源。现有Python `/capabilities`是课程技术特性清单，不直接充当业务支持判定。

需要跨Java／Python共享时，可由Java提供例如 `GET /api/customer-service/capabilities/{capabilityId}`，Python工具调用该接口；若仅同进程消费，则直接调用相同查询函数，不为接口形式额外绕HTTP。新增接口本身不会产生可信性，目录必须与真实业务实现、开关和入口能力保持一致，并由一致性检查发现漂移。

候选响应（提案，不是已有API）：

```json
{
  "capability_id": "stock_notification",
  "channel": "customer_service_agent",
  "support_status": "unsupported",
  "scope": "到货与补货提醒登记",
  "explanation": "当前客服助手不提供到货或补货提醒。",
  "alternatives": ["稍后主动查询商品库存"],
  "version": "service-capabilities-v1"
}
```

支持状态至少区分supported、unsupported、unknown；配置缺失不默认unsupported。接口超时属于本次查询失败，不能当成该功能未支持。supported还需要说明范围，不代表某账号有权限、某订单符合条件或动作已执行；具体资格继续由原业务接口校验。

### 为什么不再优先增加required_notice

能力结论和对外说明统一来自查询结果，无需在Prompt、关键词补句与多处代码各维护一份规则。输出端仍要呈现能力结论，但可以直接消费接口的explanation与经过校验的可行下一步，不再让模型生成后靠某个固定短语是否出现来补丁式判断。

MVP可将能力结果作为一个独立答复项，由现有服务端文本组装呈现，不必改前端。模型仍自然表达其余已核实事实与解释。若让模型整段自由改写，接口的正确结果仍可能被省略，所以必须验收“每个已识别问题都获得明确结果”，不能只验收接口成功。这是输出完整性的通用要求，不是为到货提醒另设一条文本规则。

### MVP顺序与验收

1. 先列清少数已核实的业务能力及服务渠道，建议从到货提醒、换货办理、真人接管的边界开始；用户尚未冻结具体清单。区分助手不能办理、商城不提供和人工入口仅为占位，避免把技术特性当业务承诺。
2. 定义一个能力查询契约和单一维护来源，使用现有身份与权限边界，只返回当前入口的业务信息；一次只返回本轮相关结果，不把整张能力表塞进模型上下文。
3. 接入单纯能力咨询及“价格＋提醒”混合咨询，使用同一能力结果生成答复，不增加多Agent或第二次模型审核。
4. 验证支持／不支持／未登记／查询超时、纯咨询／混合咨询／否定诉求，以及能力配置与实际业务入口一致。已支持仍核验资格，查询不执行动作；不支持的功能不能生成申请、提醒或真人受理记录。然后再按原失败用例真实复验。

### 新核查的官方依据

- [Anthropic：Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)：建议围绕有价值任务设计少量工具，返回相关且有意义的上下文，将适合代码承担的计算移到工具中；不建议机械地把每个后端API包装成一个Agent工具。因此“查询服务能力”应作为明确业务任务设计，HTTP或函数只是实现形态。
- [Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)：先选择合适的工作流和能力接口，按实际收益增加复杂度；不等于将最小diff作为产品目标。
- [OpenAI官方文档：Function calling](https://developers.openai.com/api/docs/guides/function-calling)：边界和返回值需要清晰，已知信息尽量由代码承担。
- [Microsoft HAX：Make clear what the system can do](https://www.microsoft.com/en-us/haxtoolkit/guideline/make-clear-what-the-system-can-do/)：支持任务与服务边界应能使用户形成准确预期。

## 3. 先区分三种情况

以下为产品答复规则，不要求本次新增状态机或注册中心。

| 已知情况 | 应有答复 | 不应混淆 |
|---|---|---|
| 已确认不支持：到货／补货提醒 | “目前不支持到货或补货提醒。” | 不是接口暂时故障，也不说稍后会通知 |
| 支持查询，但本次接口失败：查库存超时 | “目前暂时无法核实库存。” | 不说项目不支持查库存，不猜价格库存 |
| 未有可信能力或政策依据 | “目前还不能确认是否提供这项服务。”必要时问清功能对象 | 不把没有查到等同于确定不支持 |

支持的部分依原工具／Workflow完成，询问能否办理不等于授权执行。维修、换货、部分退款及人工入口已有各自业务出口，应沿用，不能被新的“统一不支持”话术覆盖。

特别注意：`backend/resources/agent_capabilities.json`主要是memory、mcp、rag等技术功能标记，不是客户业务服务的完整支持清单。本次不把它直接转换为业务能力判断依据。

## 4. 最小工程方案

### A. 将确定的不支持说明标成本轮必答内容

复用`product_query.py:34`的wants_stock_reminder识别本次正向询问／请求，保留否定语义。本轮范围只落地已有明确规则的到货／补货提醒；纯能力询问“支持到货提醒吗”也应纳入识别样例，不因为缺少商品名追问选款。

在现有商品outcome中增加一个可空的内部字段`required_notice`，值为固定句“目前不支持到货或补货提醒。”没有相关诉求则为空。由服务端已知规则生成，不接收客户端传入，不让模型决定是否支持。是否问价格、库存或指南，继续使用原有证据需求与工具路径，不新建多意图规划器。

将该字段传到最终模型的payload，明确它是本轮必须保留的能力结论。原有fallback_answer仍保留该句。复用现有模型上下文表达，不增加新的模型调用；若现有payload可直接携带该说明，则优先复用，不额外造公共API字段。

### B. Prompt补正面要求

当前final_answer_style.md已有不能承诺提醒的禁令，仍不足以保证答全。建议补充：

> 客户询问或请求当前不支持的功能时，明确说明不支持，继续回答本轮其他能回答的问题。服务端给出的必答能力说明须保留原句；不要以省略该问题代替回答，也不要把暂时无法核实说成不支持。可给出当前确实可行的下一步。

只有这句能力说明保持固定，商品事实／指南的自然表达继续交给模型。理由只使用已确认事实，不自动解释为技术限制或开发中，不承诺上线时间或真人已接手。

### C. 删句之后仍检查答复完整性

保留原有承诺清理，随后执行必答检查：有required_notice且最终文本没有该固定句，就追加一次。**模型完全没提提醒、因而没有触发承诺检测时，也必须执行此检查。** 这正是仅在“检测到越权承诺”的分支里补句无法覆盖的情况。

模型已包含固定句则不重复；首版不再用另一个模型判断各种同义表达，而是要求模型原句保留，换取可测试性。若模型改成同义拒绝，可能出现近义重复，这是窄实现的表达代价；不能用泛化的“答案含不支持就算通过”，因为它可能在说另一项功能。

检查要覆盖正常生成、删句、生成失败fallback以及跳过生成的早返回路径；不能只在customer_service_agent.py:1342之前补一次，漏掉:1314的返回。实现时优先收敛在现有最终回复收尾处，不复制多套逻辑。若整段都是承诺，继续退回已核实事实与固定说明。

纯能力询问无需商品事实或商品选择；混合咨询正常查商品。如果定向检查发现纯询问被路由或选品拦截，须在当前路由／商品入口补一个窄案例后完成，不将其宣称为已经覆盖的路径，也不引入新Agent。

### D. 只补必要观测

在现有最终生成Trace事件增加“有无必答说明、是否补回”两项状态，记录能力名称即可。不保存完整删句前原文、账号信息或额外私有提示词。本次无需为一个漏答建立新日志系统。

## 5. 验收标准与顺序（待实施后执行）

| 场景 | 必须验证 |
|---|---|
| 原失败输入，模拟模型只返回价格库存 | 没有触发承诺检测也补不支持说明，保留已核实数字 |
| 原失败输入，模拟模型返回事实＋提醒承诺 | 清理承诺后保留事实、补能力说明 |
| 模拟模型只返回提醒承诺 | fallback仍有可信事实及能力说明，不出现登记成功 |
| 模型已按要求给出固定说明 | 不重复追加，其他自然话术保留 |
| 只问“支持到货提醒吗”，没有商品名 | 回答不支持，不要求先选择商品，不查询无关商品 |
| 只问价格，或说“不要到货提醒” | 不追加未被询问的功能说明 |
| 库存读取失败，同时询问提醒 | 不编价格库存；分别说明暂不能查库存、提醒不支持；不启动售后 |
| 模型不可用／跳过生成 | 必答说明仍在；原确定性与故障边界保持 |

先用模拟生成复现并通过针对性回归，再运行原失败输入与纯能力询问两个新真实会话，必要时才扩展。加载日常服务依用户后续实施范围执行，本轮不重启。真实验证继续保留响应、Trace及业务状态不变证据。已有五会话结果不覆盖，不将本方案写成通过结果。

成功标准是客户能明确知道“不支持提醒”，其他可答问题仍正确，没有虚构动作、事实或业务写入。不是只检查输出没有“已开启”。本次不声称覆盖所有未支持功能或所有隐晦、否定、引用、跨轮表达；出现新的能力咨询时，先补可信支持状态与实际样例再扩展。
