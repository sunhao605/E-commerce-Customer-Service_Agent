# 取消闭环验收

日期：2026-10-11。首版按“语义明确且达到下限才自动取消；不够确定时保留办理并提供可操作出口”验收。`CANCEL_SCORE_MIN=0.9` 保持不变。此次没有修改 Jev 问题、DeepSeek 复核指令、分流门槛或复合任务能力。

结论：新样本两轮32次符合冻结的预期；真实低分页面取消可完成；固定模型下24项页面/接口及业务哈希检查通过。发现并修复了冲突卡选择保留后无法继续点击提交卡的问题。仍只完成隔离验证，日常8081/8000没有更新，开关默认关闭。

## 首版标准与范围

- 当前本人有效、尚未提交的退款办理；合成订单 ORD9801、ORD9802，内存 H2。
- 明确继续、犹豫、未核实条件、购买订单、另一笔售后、复合请求均不得直接取消当前草稿，不得换掉当前订单或改草稿内容。
- 明确停止可自动取消，或返回带取消按钮的确认卡；分类为停止本身不计业务成功。
- 点击取消后清草稿和凭证，旧卡提交被拒绝，下一次进入 Python 聊天时旧待办清除。
- 冲突卡不能提交。保留后，已具备提交信息的草稿返回新提交卡；选单和补原因阶段仍不能提交。

## 本次修复

复现：有待提交卡 → 固定模型制造决定冲突 → 点击「保留当前办理」 → 草稿仍为CONFIRM_SUBMIT，但恢复凭证被清空，页面所有历史卡失效，没有可继续操作的提交卡。见 [修复前结果](before-fix/result-scripted.json)、[修复前对话](before-fix/dialogue-scripted.json)。

根因是 `resumeConflict` 的KEEP分支清掉冲突凭证后只返回纯文本。现仅对CONFIRM_SUBMIT草稿生成新提交凭证并复用 `pendingRefundResponse`，内容和草稿版本保持不变。其他阶段沿用原回复。新增5行生产代码，前端无需修改。见 [本轮差异](change.diff)。

回归证明：新提交卡按钮可用，新凭证与服务端草稿一致；旧冲突卡重复KEEP为403；冲突卡伪造提交为400；取消后重复请求为409；修改原因后旧冲突卡禁用且后端拒绝；选单与补原因的保留不会获得提交按钮。该共享方法也服务RETURN，因此固定模式额外准备已签收合成订单ORD9803，实际页面验证保留后卡片类型仍为退货退款，且新卡取消成功。真实模式只使用ORD9801/ORD9802，未扩大真实模型样本范围。

## 测试器失败单列

首次脚本遗漏固定模型的占位Key，实际进入模型不可用回退；随后缺少卡片类型断言，把普通提交卡当成冲突卡发送了CONFIRM_SUBMIT，在该次临时H2新增一笔待审核售后。这次业务哈希检查失败，不能归入“全过程没有业务写入”。没有审批或退款，没有连接日常MySQL。

已补占位配置、冲突卡前置断言及结果文件的无调用处理，旧失败证据放在 [harness-before](harness-before/checks-scripted.json)。第二次真正复现生产KEEP问题，还因测试器读取被JSON省略的空token产生KeyError；测试器改用get读取，原结果保留在before-fix。两次最终验收重新创建了内存H2，业务表均未变化。
