实现放在现有调用链中，未增加模型阶段、依赖或业务工具：

1. 原路由调用新增 `inquiry_topics` 和 `answer_order`（按问题顺序引用主题、能力、业务事实，代码过滤未计划项），解析区分 missing / empty / invalid_type / unknown_id / duplicate / too_many。合法主题保留，非法局部字段不丢主意图或能力计划；规划再次校验知识域兼容性，无模型时明确标记 no_model，不猜主题。
2. 六份 Markdown 用 `<!-- rule {…} -->` 标注稳定身份、主题、范围、完整正文和必要依赖。共54个单元（含规范来源引用）、47个主题；版本均为 `2026-10-17.1`，release-manifest 同步。叠加正文只由活动文件维护，会员文件按身份引用。规则与条件对应见[规则映射](规则映射.md)。
3. 检索小块绑定完整规则，220/30 的物理切块不再决定可发送边界。选择先检查已有候选的来源与有效期，只有已取得有效证据的知识域才可从同一快照按主题取完整单元；不会在商品身份失败后仅凭主题补出旧指南。条件缺失／同身份同范围版本或正文冲突产生缺口，不取第一条。
4. `_compose_final_answer` 在目标只读知识出口先选择内容，生成、一次修复、最终无模型备用稿及同类跳过模型出口复用结果。`verified_summary` 重新从受控事实与选中规则形成，不再使用旧摘要。仅为识别商品而查询时，不把未问的价格库存送入正文或生成证据。
5. off / shadow / enforce 保留原检查含义，shadow 不因 judge 故障替换答复；off/shadow 仍保留原语义守卫。修复上限不变，有内容缺口不新增修复资格。跳过检查的出口仍标记 not_reviewed；选择与候选记录进入原有100条有界内部审阅。
6. 主题选择不缓存，每次根据本轮主题和有效时间执行；已有检索缓存只存检索结果。索引版本包含快照与完整规则切分版本，加载快照改变时重建索引。磁盘修改并不等于日常服务发布。

`knowledge.py` 的旧结果仍用于检索／澄清及 Workflow 中间环节；调用方已逐处核对，目标只读 answer_user 最终出口统一经过上述选择，不把旧中间摘要重新送入正文。澄清、安全、资格和高风险 Workflow 的原职责及授权不扩展。

## 示例、成本和未测范围

`examples.json` 保存三条离线检索＋固定主题＋真实选择／备用稿结果：叠加＋提醒585字、叠加＋退券609字、退款到账74字。前两条长度仍受完整活动与券条件影响；目标是相关且不重复，不以字数单独判合格。提醒样例沿用基线“未提供能力事实”的 fixture，正确显示尚未查到支持状态，不能误称接口真实不支持。

这组示例只是内容机制定向对照：新增主题由fixture提供，不能当作相同真实路由输入下的前后质量分数。最终知识快照 `knowledge-669e2fc4af88`。

路由输出上限由256调整为512；三知识主题＋双能力＋商品事实及呈现顺序的紧凑ASCII样例为432字节，以字节长度作本地保守容量检查，并测试截断JSON安全回退。没有把别家 tokenizer 当供应商实际用量。主题表增加输入token，512仅是输出上限，实际成本和P50/P95均待真实冻结实验；既有实际usage和调用计量仍沿用。生成至多初稿＋一次修复，judge至多两次，未增加HTTP自动重试。

备用稿使用同次路由的受控 `answer_order`，支持先能力后知识等跨类别顺序，各规则的条件随本主题保留；未提供顺序的旧路由仍按事实、知识、能力回退。新增 `test_cross_category_order_and_conditions_follow_route_order` 验证顺序与未计划项过滤。真实模型是否准确识别顺序与主题尚未验证，因此不将F4的完整体验要求标为已验收。

没有进行真实模型／Embedding外呼实验，没有重启日常服务或数据库，没有改凭据、模型型号、取消开关或阈值，没有操作真实订单、资金、通知或真人客服。下一停点为冻结真实路由→选择→生成／judge的独立样本及预算，覆盖六领域和混合问题，并验证公开正文／历史一致后再判断日常加载。
