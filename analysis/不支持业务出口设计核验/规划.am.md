## 1. 判断与客户场景

**客户已经说清楚要换货，系统应说明当前办不了换货，而不是再次问需求或替客户准备退款。** 当前没有真人接管能力。用户明确要求先放置入口：展示确认卡，确认后进入独立页面，提示“人工客服功能开发中”。

首版目标是准确停止错误办理，并说明真实可用的下一步。完整换货、维修、部分退款和真人坐席建设另行排期。占位入口已接入商城；真人服务和完整换货办理仍未实现。

示例（拟定话术）：

> 客户：收到时就破了，我只要换一件，不要退款。
>
> 客服：你希望处理商品破损并换一件，不是退款。当前客服助手不能办理换货，本次没有创建换货或退款申请。人工客服功能开发中。你可以确认前往人工客服说明页面，或选择暂不前往、留在当前对话。

“查看记录”只帮助核对已有申请，不是换货提交入口。占位页不代表真人办理渠道已开放，不能虚报接入或受理状态。

## 2. 当前证据与问题

上一轮设计阶段执行现有函数，禁止网络调用，没有运行完整 `chat` 或访问业务数据库。4条构造输入及2项契约断言完成；详见[原始记录](../../analysis/不支持业务出口设计核验/current.json)和[复跑脚本](../../analysis/不支持业务出口设计核验/check_current.py)。这是当前行为诊断，不是优化后通过成绩。

## 3. 首版业务边界

| 客户实际诉求 | 首版应做什么 | 不应做什么 |
|---|---|---|
| 换货、维修、补发、质量问题处理 | 保留原诉求，明确本助手不能办理，说明可核实入口或入口缺失 | 改成无理由退货，承诺已受理、换新、运费承担 |
| 只退一件、退部分金额、部分退货 | 说明目前只能办理符合条件的整单流程 | 自动扩大成整单退款，默认金额或件数 |
| 本人未发货整单退款、符合条件的七天无理由整单退货 | 沿用现有核验及本人确认流程 | 因出现“退货／退款”就一律阻断 |
| “质量问题怎么办”“换货规则是什么” | 解释已核实政策与本助手办理边界 | 把咨询当成申请，清掉原退款草稿 |
| 只给订单号、只说帮我处理一下 | 保留 `unknown`，澄清目标 | 猜换货、退款或其他办理 |
| 否定换货，明确要求未发货整单退款 | 识别客户最终明确的受支持目标 | 仅因出现“换货”二字就拦截 |

质量描述本身不等于新的办理指令。“商品坏了”不能被改写成“七天无理由”；也不能据此断言客户没有任何售后权利。涉及真实政策判断时只回答已核实依据。

## 4. 最小实现方案与取舍

按用户补充要求，复用商城卡片与路由，不新增Python意图标签。Java网关在调用模型和准备售后之前拦截明确的不支持业务。固定Agent即使误判退款，也不能让这些请求进入整单流程。此前新增`unsupported_service`标签的建议由本轮方案替代；Python独立工作台不属于本次接入范围。

维修、部分退款／退货、换货、补发、质量售后，以及客户主动要求人工客服，都返回`pendingAction=HUMAN_SUPPORT`。其他Agent路径返回`next_action=transfer_to_human`且没有有效审批Workflow时，也提供同一张卡。退款审批继续使用业务卡，不引向开发中页面。

人工卡复用现有`confirmRequired`、标题、摘要和`actions`。动作是`OPEN_HUMAN_SUPPORT`（确认前往）和`STAY_WITH_AGENT`（暂不前往）。前端单独处理导航，不调用售后`resume`，不生成换货、退款或人工服务申请。

新会话没有提交凭证。原退款草稿保留时，响应沿用原凭证，让原业务卡继续有效；它不是人工交接凭证。明确改办未支持业务时，服务端清理原草稿凭证，前端禁用旧卡；向服务端重发旧凭证也不能提交。

### 4.1 改口与旧确认卡

已有未提交退款，客户明确说“不要退款，改换货”：原卡与凭证失效，新回复只有人工入口卡。已提交申请不撤销。只问换货政策或单独要求人工入口时，保留原草稿，进入或退出说明页不修改申请。

识别规则覆盖明确业务词与直接否定。否定换货／人工后明确申请整单退款仍走原流程。复杂组合任务和所有自然语言表达的覆盖未纳入首版。局部规则验证不代表真实模型识别率。

### 4.2 占位页与可扩展位置

点击前，人工卡就说明功能开发中。确认后进入`/human-support`，显示“人工客服功能开发中”。页面明确尚未接入真人，未登记服务请求或提交售后申请，并提供“返回客服助手”。暂不前往则留在对话并显示选择结果。

占位页沿用商城路由和样式，没有外部URL、排队、工单或会话复制。后续真实服务可以替换`onHumanSupport`的导航去向与目标页内容。真实交接的身份、上下文和回执需要届时接入，不属于当前已有能力。同页往返保留对话，刷新整页仍按现有商城规则重建前端对话。

种子中的换货政策与助手办理能力分开阅读。本轮没有重置数据库政策或更改运费规则。新卡与说明页明确当前不可办理，不把示例政策变成执行能力。

## 6. 验收标准与实施顺序

以下是本轮定向验收要求，实际结果见[实现验收](../../analysis/人工客服占位入口实现验收/结果.md)。构造样本用于定向检查，不能外推真实用户成功率。

| 用例组 | 关键输入／初始条件 | 必须观察到的结果 |
|---|---|---|
| V01 明确换货 | 本人有效订单；“收到时就破了，只要换一件，不要退款” | 保留破损换货目标，展示人工占位卡，无退款／退货Workflow和业务提交卡，不创建申请 |
| V02 部分与维修 | “两件只退一件”“椅子坏了，帮我维修” | 各自说明能力边界，不是通用问候，不创建整单申请 |
| V03 防止过度拦截 | “不用换货，未发货订单我要整单退款”；明确七天无理由申请 | 进入已有资格核验和确认卡，确认前不写申请 |
| V04 仅咨询与目标未知 | 换货政策咨询；仅订单号 | 前者说明政策／能力边界，后者澄清目标；不新增办理 |
| V05 明确替换原办理 | 原退款提交卡有效；“不要退款，改换货” | 旧token／revision不能提交，新回复无卡；已提交申请保持原状态 |
| V06 回退与模型误判 | 模型不可用；固定模型故意返回退款／退货标签 | 明确不支持诉求仍不能准备或提交错误申请；安全与正常退款检查仍有效 |
| V07 出口与承诺 | 没有真人接管配置 | 确认后进入开发中页，暂不前往留在对话；不虚报转接或受理，两项均不调用提交接口 |

顺序：先用固定模型与隔离订单复现V01及V05，再做最小跨端修改；完成相关Python检查、Java编译及必要页面构建；用隔离H2与浏览器验证回复、动作、旧凭证和申请状态。逐轮保存截图和文字，比较8张业务表，V05中仅允许未提交会话状态变化。无相关新失败后停止，不自动扩大模型评测或重启日常服务。

未来出现真实运营渠道时，替换占位页并补真实交接回执。当前设计可以完成“诚实的能力边界”，仍不能让客户在本系统完成换货；这是产品能力限制，不能用更好的话术掩盖。
