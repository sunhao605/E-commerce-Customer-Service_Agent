分析与官方资料访问日期：2026-10-10（Asia/Shanghai）。范围：当前 Python Agent 的 12 个意图标签、路由 Prompt、RoutePlan 和执行分支；商城差异单独说明。证据类型：当前源码静态核验、已保存的 B01/B02 实测、官方资料与助手设计判断。本轮没有修改标签或业务代码，也没有运行新的在线模型评测。

## 判断

**当前标签适合展示课程里的 Tool、RAG、Workflow、安全与降级分流，但作为电商客服的业务意图体系，存在明确缺口。政策咨询与办理必须分开。** 问题不在于“12 个太多或太少”，而在于部分标签不能稳定表达用户目标，名称与执行范围不一致，咨询入口缺失。

不能只将失败归因于标签名称。即使改名或增加标签，知识承接、缓存、工具白名单、待办和审批边界没有同步，B01/B02 仍会失败。标签识别出“想办理”也不等于用户已经确认提交，更不等于管理员批准。

针对当前两个实测问题，**建议第一步增加 `refund_policy_query`、`return_policy_query` 两个只读标签，保留原办理标签，并明确当前 `faq_query` 仅承接发票。** 这是项目设计建议，不是以下厂商要求采用的标准标签。本轮未实施。

我此前提出“扩展通用 FAQ”的方案仍能实现，但需在 FAQ 后再判断政策主题。本项目的模型只返回一个意图。代码再按标签选择确定路径。两个明确咨询标签更直接，也更便于评测与追踪。这次评估将它作为优先建议，替代此前优先扩展 FAQ 的建议。

## 二、官方资料提供了什么依据

下面列出实际打开阅读的官方页面。各机构没有共同制定一套电商意图标签；有些直接讨论路由，有些提供交互或工具边界原则。右列是对本项目的推导，不伪装成原文结论。

| 来源与官方页面 | 已核验的原文要点，使用转述 | 对本项目的适用性与限制 |
|---|---|---|
| Anthropic：[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) | 输入分类后进入不同任务；适用于类别可区分、可可靠分类且适合分别处理的情况；客服一般问答、退款请求、技术支持是示例 | 直接支持按下游任务差异分流。政策咨询与准备申请有不同路径；没有要求每个主题新建 Agent。文章发布于 2024-12-19，本文只使用路由设计原则 |
| OpenAI：[Function calling](https://developers.openai.com/api/docs/guides/function-calling)；[Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety) | 明确名称、用途、何时使用/不使用，处理边界例子；用结构化字段约束数据流，结合代码、确认和评测 | 支持标签定义、执行契约和验证同时设计。工具数目的建议不能换算成“意图不得超过 20 个”；Agent Builder 的 MCP 审批建议也不是本项目所有只读查询必须弹确认的规范 |
| Google PAIR：[Feedback + Control](https://pair.withgoogle.com/chapter/feedback-controls/) | 自动化与用户控制需要平衡；允许用户调整、退出，金融等高影响情境尤其重视控制 | 从用户体验支持“只咨询”不能变成办理意向、应能取消当前操作。没有直接规定分类器标签数量或命名 |
| Microsoft HAX：[Disambiguate before acting](https://www.microsoft.com/en-us/haxtoolkit/pattern/g10-a-disambiguate-before-acting/) | 用户目标不确定时，行动前澄清；澄清也会打断流程，应谨慎使用 | “帮我处理退货”可以问目标；B02 已明确只咨询，不需要再强制问订单。当前固定 confidence 不等于文档中的已测不确定度 |
| LangChain：[Workflows and agents — Routing](https://docs.langchain.com/oss/python/langgraph/workflows-agents#routing) | 根据输入进入对应任务路径；示例用结构化路由字段和代码分支 | 支持将标签与可执行路径对齐。结构化输出提供形式约束，不保证语义分类正确，也不授权写操作 |
| Hugging Face：[ZeroShotClassificationPipeline](https://huggingface.co/docs/transformers/en/main_classes/pipelines#transformers.ZeroShotClassificationPipeline) | 候选标签由调用方给定；单标签与独立多标签有不同处理方式 | 说明候选集合与分类假设须明确。不能把业务目标、风险和运行状态全部当作互斥类别；本项目不是该 NLI 分类器，不能照搬其概率或效果 |
| xAI：[Function Calling](https://docs.x.ai/developers/tools/function-calling) | 模型请求工具调用，应用执行函数并返回结果；工具定义包含名称、描述与参数 schema | 支持把理解/请求与应用执行区分。该页不提供电商意图分类标准，不能借此宣称 xAI 推荐某个退货标签 |
| Nielsen Norman Group：[10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) | 用户控制与退出、概念一致、预防错误、操作提交前确认 | 支持区分了解规则与承诺行动，清楚表达提交后果。是交互原则，不是 NLU 标签算法规范 |
| Google Cloud，作为 PAIR 之外的直接分类补充：[Dialogflow agent design](https://docs.cloud.google.com/dialogflow/cx/docs/concept/agent-design) | 意图反映一轮对话的用户目标；同一目标的不同表达归同一意图；避免相近重复意图，区分意图与实体，确认可按会话场景复用 | 直接支持“目标不同则区分，同义表达不重复拆”。该文的训练短语数量要求针对 Dialogflow，不套到本项目 LLM Prompt 上 |

由这些资料与项目证据推导出的评估标准是：目标是否清楚；类别是否存在必要差异；是否覆盖当前能力。

还要检查标签名、Prompt 与执行是否一致；是否保留澄清/不支持的出口；能否按真实结果和副作用验收。这些标准没有证明任何候选方案已经有效，仍须项目复测。

## 三、政策咨询与操作应该怎样区分

**至少区分政策、具体资格、办理、已有申请状态。** “想让客服做退货相关操作”仍然太宽：读取订单判断可退与创建申请，副作用不同。

| 用户表达，以下为设计示例 | 用户真正目标 | 所需信息与允许路径 | 禁止行为 |
|---|---|---|---|
| 退货政策是什么？我只了解一下 | 了解通用政策 | 读取退货政策；无需本人订单，解释条件与流程 | 不创建办理待办、申请草稿或确认卡 |
| ORD1234 还能退吗？先别申请 | 核验具体订单资格 | 核实身份/归属，读最新订单、购买时可退属性、签收时间及政策；仅回答资格 | 不因为资格通过就准备申请或进入提交确认 |
| 帮我申请 ORD1234 七天无理由退货 | 请求办理 | 校验最新资格，补必要信息，准备本人确认；客户提交后才待审核 | 不把意图标签视为提交授权，不模拟管理员批准 |
| 我之前的退货处理到哪了 | 查看已有申请 | 只读本人已有售后申请与当前状态 | 不创建新申请 |
| 先别退了，取消刚才还没提交的操作 | 取消当前未提交意向 | 使用当前待办/草稿状态处理，明确取消了什么 | 不把未提交草稿取消说成撤销已提交申请，更不等于撤销退款 |

其中通用政策与具体资格都是只读，但信息需求不同。资格查询可以合理要求订单；不能因此把“退货政策需要什么条件”也强制绑定订单。咨询中出现否定不是取消业务记录：B01 的“不申请退款”表达当前不办理，不能编造已经存在的申请供取消。

```flow LR
用户表达 -> {用户目标}: 本句与必要待办
{用户目标} -> 读取通用政策: 咨询规则
{用户目标} -> 读取本人订单: 核验资格
{用户目标} -> 核验并准备确认: 明确申请
{用户目标} -> 读取已有申请: 查询进度
{用户目标} -> 澄清目标: 仍不清楚
核验并准备确认 -> 本人确认提交: 资格满足
本人确认提交 -> 管理员独立审核: 待审核
```

这是建议流程，不是已经实现的新标签或新路径。所有分支仍须遵守现有身份、归属与安全检查。

## 四、当前体系哪里合理，哪里需要调整

合理部分是已经把“读已有进度”与“准备新申请”分开，也将不同业务工具/政策/Workflow 接到了受控 RoutePlan。应保留这些分工。

优先调整四处：

1. **补售后政策咨询入口。** B01/B02 已提供实际失败证据，新增标签有明确路径与验收价值。
2. **明确发票 FAQ 边界。** 名称宽、实现窄；只加例子但仍让所有 FAQ 用发票缓存，会继续串题。
3. **把用户目标与系统状态分层。** 知识不足、工具故障、安全风险可以与正常业务目标同时存在。后续不要都强迫模型只选一个业务标签；当前既有 source guard 等安全检查继续保留。
4. **区分目标不清与已知但不支持。** B15 换货意图清楚，但本项目未实现完整办理；不能改成退款或假装提供了换货功能。M07 还涉及取消意向的会话状态，不只缺一个业务名词。

多轮还有独立边界：`ORD1234`、“第一笔”、“确认一下金额”不能脱离待办和当前页面解释。`dialogue_act` 如补槽、解释、确认、取消，应依赖可信会话状态；不需要为每一个“退款第一笔”“退货第一笔”复制标签。已确认的“每句仍交给模型、只附短待办、合法模型标签直接采用”保留。

复合请求也不能用“一出现高风险词就全部按办理”解决：“退货条件是什么？顺便查物流，我暂时不申请”不能只因为包含退货词准备申请。单标签首版应有明确的主诉处理与剩余诉求说明；是否改多任务输出须另行验证，不在本轮自动增加。

## 五、分两步调整，避免一次重建体系

### 第一步：针对已复现问题，12 个标签扩为 14 个

这是建议，不是当前事实；“14”是两个已复现缺口带来的结果，不是目标数量。

| 建议标签 | 定义与反例 | RoutePlan 与状态边界 |
|---|---|---|
| 新增 `refund_policy_query` | 了解通用退款条件、规则或流程；“帮我申请退款”不属于它 | `needs_rag=true`；退款政策；业务工具 false、`requires_workflow=false`、`answer_user`；无办理待办 |
| 新增 `return_policy_query` | 了解通用退货条件、规则或寄回流程；“这笔订单能否退”是具体资格，“帮我申请退货”是办理 | `needs_rag=true`；退货政策；业务工具 false、`requires_workflow=false`、`answer_user`；无办理待办 |
| 保留 `refund_request` / `return_request` | 明确想申请，不包含仅咨询或仅核验资格 | 按已有本人订单核验、确认和审核边界办理；不自动批准 |
| 现有 `faq_query` 暂时保留 | 定义收窄为当前确实支持的发票咨询 | 仍用发票政策/缓存；售后政策新标签不进入该缓存 |

两份政策可以共享既有知识加载、返回对象与最终表达代码，两个标签不需要各建一个 Agent。两种政策的商品条件、时间窗口、知识依据不同，而当前路由只输出一个标签；拆两个标签可以直接选正确政策，不必再加一次模型分类或模糊的 FAQ 主题推断。

必须同步 `Intent` 枚举、模型标签白名单、路由 Prompt 和故障兜底。还要接齐 RoutePlan、知识分支、政策引用和缓存隔离。用例与 Trace 展示也要同步。只给枚举加两个字符串不算完成。结构化 schema 可以约束合法取值，语义正确与否仍靠行为评测。

**这一步只解决通用政策入口，不宣称补齐具体资格查询、取消意向或换货。** 对具体资格表达，在专门只读能力接好前，应先说明范围并澄清，不能误入申请。原有 B01/B02 不再作为“无对应路径”的缺口排除，新增目标标签与行为标准后单列前后对照；不同版本分母变化须说明。

### 第二步：按新证据整理剩余边界

| 范围 | 建议 | 何时值得做 |
|---|---|---|
| 具体退款/退货资格 | 接只读资格路径；可明确为 `refund_eligibility_query`、`return_eligibility_query` | 有对应输入、最新事实读取与无申请副作用的验收用例时；标签先有名字不代表能力已实现 |
| 取消或确认当前意向 | 用对话动作与当前任务/草稿状态处理 | 先定义取消对象、确认对象及终态，再做 M07；不把聊天“同意”当管理员批准 |
| 标签名称不一致 | 将 FAQ 明确为发票；将售后状态名称覆盖退货 | 完成兼容、客户端和回归核对时；无需把全项目命名重构并入第一步 |
| 系统状态混进意图 | 逐步拆 `evidence_status`、`execution_status`、安全检查结果 | 真实 Trace 和来源能支持这些值时；不让模型凭空宣称服务中断或知识不足 |
| 更多业务不断增加 | 考虑 `domain`＋`goal`，对话动作另存 | 当前单标签造成大量重复或复合处理无法表达时；只允许已支持组合，不生成笛卡尔积标签和功能 |

`domain=return, goal=policy` 与 `domain=return, goal=apply` 是一种后续结构示意。它并非此次必须改成的架构，也没有官方证明比两个明确新标签更好。第一步先沿用现有单标签 JSON，减少跨端契约改动。
