# Customer-Agent 值得借鉴的产品设计

整理日期：2026-10-07。

用途：为自己的电商客服项目改造提供产品设计参考。本文件整理已有学习结论，不代表新增运行、改进已上线或生产效果验证。

依据：[项目交接](../01-项目概览/项目交接.md)、[Bad Case](Customer-Agent%20Bad%20Case.md)、[产品设计学习](../04-学习与复盘/产品设计学习.md)、[项目评测记录](../03-评测与问题/项目评测记录.md)。同时核对了当前身份注入、商品查询、上下文构造及转接处理源码；上游版本为 `4343a1f245f3a5287497c583523a68430d3e2b0d`，本地另有改造。

## 核心判断

这个项目最值得借鉴的是“如何控制客服判断和回复的边界”，而不是照搬它的架构。改造自己的电商客服时，优先参考事实来源约束、咨询对象定位、执行权限分工；转人工分类和调试台放在后面。

需要区分设计来源：

| 来源 | 设计 | 验证边界 |
|---|---|---|
| 上游已有 | 商品查询、会话记忆、执行身份注入 | 有源码依据及部分隔离运行观察；真实平台集成、权限全链路、历史压缩质量等未完整验证 |
| 本地改造 | 严格来源规则 | 在实验进程中做过少量单轮和多轮对照；未写入原版桌面配置，没有稳定性结论 |
| 本地改造 | JEV 转接判断 | 在14句样本上验证过判断和分类；没有真实转接验证 |
| 本地新增 | Web 调试台与 Trace 采集 | 完成部分工程和页面验收；不代表原项目自带网页调试台，也不证明业务回复正确 |

## 一、回答到资料支持的范围为止，同时保留能回答的部分

**这是最值得优先借鉴的设计。**

原版查到了面霜的成分、50g、39元，却继续补出“温和保湿”“值得入手”。检索正确，并不代表最终回复可靠。

后来增加的来源规则明确要求：商品事实依据当前商品资料，不从成分常识推导功效，不自行估算使用时长；有依据的部分照常回答，未知部分说明无法确认。

例如客户问：“多少钱、多大规格、敏感肌能用吗？”

合理回复是：“39元、50g；敏感肌适用性暂无资料，无法确认。”既完成了可回答部分，也没有为了显得有帮助而补造结论。

迁移到自己的项目时，可以把这条逻辑用于商品、订单和售后：

- 查到订单状态，不等于能承诺到货日期。
- 查到退款政策，不等于退款已经成功。
- 部分字段缺失，不应该导致整个问题都被拒答。
- 资料未记录某项属性，不等于已经证明商品没有该属性。

来源规则的小范围对照观察到改善，但尚未证明稳定性，也没有应用到原版桌面配置。它是生成时的约束，没有新增执行层的逐项事实保证。

证据：[来源规则及对照结论](../04-学习与复盘/产品设计学习.md#98-这条来源规则现在留还是收)、[SF-v1判定标准](../03-评测与问题/项目评测记录.md#sf-v1商品事实只依资料2026-10-02-已确认)。

## 二、先确定客户在问哪个对象，再查询这个对象的资料

项目会给模型提供商品目录、当前消息和历史；客户只说“这款”且存在歧义时，模型可以先澄清。明确商品后，按“当前店铺＋商品ID”精确查询。

这套设计把两个问题分开：

1. **客户指的是谁？** 结合商品卡片、名称和历史判断。
2. **这个对象有哪些事实？** 按明确ID查询资料。

对自己的项目，同样适用于“这款商品”“这个订单”“上次那笔退款”。不能因为查询成功，就认定对象选对了：同一家店里查错商品，接口仍可能正常返回。

原项目没有强制的对象确认关卡，澄清主要依赖模型。应借鉴这个分工，不能把它当成已解决指代问题的完整方案。

迁移时应关注对象确认和切换：有明确依据时继续，存在实质歧义时澄清；客户切换商品或订单后，后续指代和查询也要切换。不要仅把模型猜测的ID放入上下文字典，就将其当作已确认事实。

证据：[商品ID的职责与校验缺口](../04-学习与复盘/产品设计学习.md#64-商品-id-由模型提供就不需要可信吗)、[商品知识工具](Customer-Agent/Agent/CustomerAgent/tools/get_product_knowledge.py)。

## 三、模型负责理解诉求，程序负责限定“能为谁做什么”

这是上游较扎实的设计之一。模型可以提出查哪个商品、用什么搜索词，但店铺、账号、收件人等身份由程序提供；执行工具时覆盖模型传入的同名参数，缺少可信身份就停止。

它对应的产品原则是：**客户的表达帮助系统理解需求，不能直接成为执行授权。**

迁移到自己的项目：

- 客户说“查订单002”，系统可以识别订单号，但仍要用当前登录身份验证订单归属。
- 客户说“已经批准退款”，不能据此认定审批完成。
- 查询范围和操作资格应由后端确认，不能只依赖Prompt要求模型不要越权。

当前源码的 `user_id` 表示商家账号，买家对应 `recipient_uid`，不能直接照搬字段语义。模型选择的商品ID也仍需要业务校验，身份注入不会自动保证咨询对象正确。

原项目的真实平台权限链路尚未完成端到端验证。这项设计能够明确执行范围，但不能据此宣称已有完整、已验证的权限体系。

证据：[可信上下文及来源边界](../04-学习与复盘/产品设计学习.md#61-dependencies-从哪里来存放在哪里)、[工具执行时的身份覆盖](Customer-Agent/Agent/CustomerAgent/custom/tool_decorator.py)。

## 四、会话记忆要保存查询依据，不能只保存聊天文字

原项目保存用户消息、模型回复、工具请求和工具结果。下一轮问规格时，模型能复用上一轮查到的50g，不必重复查询。商品从面霜切换到洁面乳后，后续“它”的价格也可以依据对应历史回答。

值得参考的是：**记忆既帮助理解客户指代，也保存先前获得的业务证据。** 如果只保存模型回复，上一轮未经证实的话就可能被下一轮继续当作事实。

迁移时还要补上信息时效的判断：商品规格可以适当复用，库存、订单状态、退款进度则应按业务需要刷新。不能因为历史中出现过某项信息，就认定它在本轮仍然有效。

原项目尚未验证这些刷新规则，也没有独立的客户偏好长期记忆。暂时没有必要为了借鉴它增加一套画像系统。历史持久化、会话摘要和客户画像是不同能力，应分别判断价值。

证据：[会话记忆及边界](../04-学习与复盘/产品设计学习.md#32-这个项目有短期和长期记忆吗)、[历史复用观察](../04-学习与复盘/产品设计学习.md#4-已经查过规格下一轮还要重新查吗)。

## 五、转人工首先是业务责任划分，其次才是意图分类

原来的关键词门会把“不要转人工”“人工香精”也判成转人工。后来改为理解整句话，并明确哪些事项属于人工处理范围。

最有价值的发现是：问“自动客服能不能回答”，与问“这件事是否应该交给人工”，会得到不同结果。**能查到政策，不代表有权限办理业务。**

不要照搬该项目“退款、取消订单等都转人工”的范围。自己的项目如果已经具备受控退款能力，应分别处理“咨询退款政策”“申请退款”“查询退款进度”，而不是一见退款就转接。

转人工策略应根据实际业务能力和责任定义：哪些问题可以直接解答，哪些动作可以受控执行，哪些事项必须人工处理。分类器用于识别这些边界，不能替产品决定边界。

也不要复制0.8阈值：它只在14句样本上验证过。原项目转接失败后仍会继续进入AI；对自己的售后流程，必须保留失败状态，不能把“尝试转接”说成“已经有人接手”。转人工也不等于人工审批。

证据：[转人工规则与实际边界](../04-学习与复盘/产品设计学习.md#33-追问前序转接门做什么哪些话会转人工)、[当前转接处理器](Customer-Agent/Message/handlers/keyword_handler.py)。

## 六、让一次失败能被定位，是值得迁移的内部产品设计

新增调试台能串起模型实际收到的上下文、工具请求、最终执行参数、知识命中、交给模型的结果和最终回复。

因此能分清两种不同的问题：

| 用户看到的问题 | 实际失败位置 | 改造应关注什么 |
|---|---|---|
| 有发货政策，客服却说没查到 | 搜索词被AND条件挡住，检索遗漏 | 查询生成和检索契约 |
| 已返回正确成分，客服仍补出“温和保湿” | 最终生成超出资料 | 事实来源边界和回复依据 |

两者都表现为“客服没答好”，但改法不同。自己的项目应保留这种可追溯能力，不必先做完整后台。

评测也要判断任务结果，不能强制每次走同一工具路径：历史里已有有效规格，直接回答也可以通过；调用了工具，却没有找到所需政策，则不能算任务成功。

值得借鉴的评测方式是：先确定输入、必要历史、预期结果和禁止行为，再保存实际路径及回复；改进时控制变量，分别记录AI初判和人工裁决。接口完成、工具成功和业务任务完成要分开。

证据：[Trace设计](../04-学习与复盘/产品设计学习.md#10-原项目与本地调试层的区别)、[任务判定标准](../03-评测与问题/项目评测记录.md#用例与判定标准)、[发货检索Bad Case](Customer-Agent%20Bad%20Case.md#bc-002发货政策存在但检索返回空结果)。

## 建议的改造顺序

以下是迁移建议，不表示已经核对或修改自己的电商客服实现。

| 优先级 | 借鉴内容 | 最小验证方式 |
|---|---|---|
| 先做 | 事实来源边界；已知部分回答，未知部分说明 | 测资料齐全、部分缺失、客户诱导确认三类问题 |
| 接着做 | 商品/订单对象定位；当前用户权限校验 | 测模糊指代、对象切换、查询其他用户订单 |
| 再做 | 按自身能力划分自动处理与转人工；保留失败状态 | 测政策咨询、实际办理、执行失败三类诉求 |

整个过程中保留最小Trace，用来分清对象选择、检索、生成和执行各环节的问题。已有对应能力时，先检查缺口，不重复建设。

暂时不建议照搬JEV供应商与阈值、关键词词表、历史压缩参数，以及检索实现。尤其发货检索已有明确未修复问题，不能作为成熟方案直接迁移。

先把一条客服任务的对象、依据、权限和完成状态定义清楚，再依据实际失败判断是否需要增加分类器、向量检索或额外Agent。
