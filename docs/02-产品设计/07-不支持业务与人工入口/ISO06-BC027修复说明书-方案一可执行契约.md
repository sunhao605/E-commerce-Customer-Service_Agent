# ISO06／BC-027修复说明书：方案一可执行契约

日期：2026-10-16｜编号：BC027-FIX-CONTRACT-001｜版本：1.0

状态：用户已选择方案一；本文是给Coding Agent的实施与验收契约，**不是修复完成报告**。下文新增字段、接口和用例均为待实现要求，不代表当前源码已有。本文优先于此前分析中“删除故障转人工出口”“所有转人工建议均不允许”等已被用户纠正的推导；原始响应、冻结清单和历史成绩不改。

## 1. 任务与完成标准

实现一种通用于商品、订单、物流、政策等只读咨询的约束：**模型可以自然解释事实并提出有依据的下一步，但不能把用户入口、条件建议、助手代办和真实受理混成一件事。**

成功同时满足：

1. 部分查询成功时，保留已核实事实；失败／unknown只影响对应事项，不被说成业务不支持。
2. 工具失败后仍可澄清或引导用户要求人工；澄清必须能补齐实际缺口，不能把接口故障一律变成追问。
3. 商城已有人工入口时，允许提示用户在对话框要求转人工，复用用户确认卡与导航；不代收联系方式、提交转接、承诺接手或回电。
4. 生成、一次judge和备用稿使用同一份可追溯的事实与下一步边界。自然同义表达不依赖关键词判断。
5. 退款／退货草稿、商品候选、待补政策、确认凭证及既有审批边界不因回复检查改变。
6. 完成工程验证时只报告工程结果；真实语义效果、商城联调、运行加载分别有独立证据，不互相代替。

采用方案一：保留自由、自然的整条回复与一次现有judge。**不切换为整条模板渲染，不增加第二个judge、Agent、自动重写循环或自动补查工具。**

## 2. 失败事实与归因边界

用户原话：

> 轻量露营折叠椅目前多少钱，还有库存吗，能登记到货提醒吗？

隔离fixture查到199元、库存0；能力查询注入HTTP503。实际回复：

```text
轻量露营折叠椅目前标价 199 元，不过现在是无库存状态。

到货提醒这块，我这边暂时没法确认能否登记，需要再帮您核实一下。您也可以留下联系方式，我帮您转人工进一步确认。
```

judge三项pass、decision=allow，原文被发出。错误位于留资并由助手代办进一步核实的承诺；没有实际采集联系方式、转接或业务写入的观察证据。

已确认：

| 环节 | 源码／轨迹证据 | 修复责任 |
|---|---|---|
| 提示组合 | `backend/resources/prompts/tool_usage.md:3`要求故障时澄清或转人工；ISO06实际同时加载tool_usage与final_answer_style，两份指纹与冻结一致 | 保留产品目标，补清谁发起、需要何种确认、允许产生什么效果；不直接删掉人工出口 |
| 共享证据 | `backend/agent/answer_review.py:75—94`只接受RoutePlan内能力；本例只有库存与提醒失败结果，无人工入口阶段信息 | 补业务维护的交互边界，不把所有入口硬塞进RoutePlan.capability_ids |
| 生成 | `backend/agent/models/answer_client.py:123`在enforce中用review_context作完整payload | 将下一步边界并入共享快照，禁止自行扩展办理路径 |
| 检查 | `backend/resources/prompts/answer_judge.md:7`重点覆盖已做与持续代办；本例公开理由把整句视为普通建议 | 扩展同一维度对即时／未来办理承诺的检查，保留合法条件建议 |
| 出口 | `backend/agent/customer_service_agent.py:1401—1408`按judge决定互斥选择正文 | 复用现有出口，不能正则删一句后直接放行 |

规则缺少阶段区分、证据缺口及漏放是事实；尚无实验能证明某一句Prompt单独造成此次生成，不能把推测写为模型内部原因。Routing按原请求未查人工本身不算错误，不为修本例新增主意图或强行查询全部能力。

## 3. 已确认的产品边界

| 行为／状态 | 合同要求 |
|---|---|
| 用户主动要求人工 | 用户可在对话框要求转人工，商城展示现有确认卡；不得因真人未完成就删除或误拦此入口 |
| 故障后引导 | 当前渠道有可核验入口时，允许引导用户提出人工请求；不主动代提交信息，不要求留资来履行虚构服务 |
| 用户确认前往 | 仅触发现有导航，不调用售后resume，不提交工单、售后或通知 |
| 用户暂不前往 | 保持当前对话和既有业务状态；不能借此取消退款、提交申请或清空草稿 |
| 目标页 | 沿用“人工客服功能开发中”，说明尚未真实转接、登记请求或提交售后 |
| 对话及确认卡 | 沿用既有文案分工，**不统一新增“开发中”提示**；但不得声称已受理、已接手或已安排联系 |
| human_takeover=unsupported | 仅描述当前未实现真人接管；不能推导为没有用户入口，也不能为支持入口将该状态改成supported |
| Python独立工作台 | 不自动拥有商城卡片和导航；若引用商城入口，必须明确“在商城客服对话中”，不能声称当前页面已出现按钮 |

旧规划与实际入口：[人工出口PRD第4.2节](不支持业务清晰出口产品需求规划.md#42-占位页与可扩展位置)；`CustomerServiceGatewayService.java:119—125`、`:756—770`；`ecommerce-backend/frontend/src/shop/App.tsx:1109—1114`、`:1204—1208`。这些是源码核对，未重新核验当前运行服务。

## 4. 必须实现的来源契约

### 4.1 由业务端维护入口事实

采用一个小型只读交互策略，不建立通用动作注册平台：

- 在现有`ecommerce-backend/src/main/resources/service-capabilities.json`增加`interactionPolicy`节；复用现有channel及版本来源，不另建Python支持表。不改已有能力支持状态、业务解释或种子数据。
- 由`ServiceCapabilityCatalog`加载并校验；`ServiceCapabilityController`增加字面量路由`GET /api/customer-service/capabilities/interaction-policy`，返回现有ApiResponse封装。该接口**目前不存在**。
- 该精确路径与`/{capabilityId}`共存，应测试不会被当作未知能力ID。复用现有GET能力接口鉴权，不放开匿名访问，不新增凭据。
- Java元数据描述的是实际已有入口，不提供执行服务。复用既有卡片动作代码和目标surface；不得引入模型指定的URL、工具名或任意导航。

最小数据语义如下，字段名称允许随现有Java序列化风格统一，但不得丢失或混并含义：

```json
{
  "schemaVersion": "interaction_policy_v1",
  "channel": "customer_service_agent",
  "version": "<业务资源版本>",
  "entries": [
    {
      "id": "human_support",
      "surface": "mall_chat",
      "status": "available",
      "actor": "user",
      "initiation": "message_request",
      "confirmationRequired": true,
      "completionEffect": "open_entry",
      "destinationState": "placeholder"
    }
  ]
}
```

`available`只表示入口可用，`completionEffect=open_entry`只允许解释前往入口，不是提交、排队或受理凭据。`placeholder`供生成与judge理解阶段，不要求在所有对话里照抄内部状态。入口ID不是新业务能力ID，不加入RoutePlan或注册为模型工具。

### 4.2 Python来源与失败语义

- 在现有`agent/service_capabilities.py`复用HTTP读取模式，确定性获取上述策略；每个适用请求至多一次，无重试、无新缓存。HTTP连接／读取等超时参数各不超过2秒，另记录实际总耗时，不将局部HTTP超时当整条对话截止；这是业务只读开销，不计为模型调用。
- 仅对现有eligible最终答复路径取策略；不扩展安全、缓存、澄清、审批／Workflow等直出路径的judge覆盖，不因取策略新增工具执行。
- 复用现有业务base URL与服务身份，`trust_env=False`；验证success、schemaVersion、channel、版本、字段类型、ID唯一性及枚举。状态不全、接口错误、超时或未知版本一律为**交互信息未确认**，不是入口不存在。
- 来源限受控业务HTTP结果。用户消息、历史、模型输出、任意`runtime_context`中的同名字段不能覆盖或伪造该结果；不要因为字段叫trusted就当成经过认证。现有调试`/chat`的身份体系不在本次重写范围。
- 该业务策略只证明`mall_chat`入口存在，不证明当前调用者正在商城。为避免引入新的调用方鉴权，本期对该入口的生成引导统一指向“商城客服对话”，不依赖未经认证的`mallAfterSaleRouting`等字段宣称“你当前页面有按钮”。Java自身的真实卡片仍按既有路径呈现。
- 对错误策略保存最小failure和source状态，不记录认证头、Cookie、令牌或个人信息；不得回退读取本地JSON并冒称在线结果。

不允许用“给所有capability_ids追加human_takeover”替代此契约，也不允许每次查询整份能力目录。接口暂不可达时，保留已有事实和对应未知说明，不替顾客补出转接服务。

## 5. 共享快照与下一步契约

在`build_review_context`中增加交互策略证据和`allowed_next_steps`；复用当前有界内部review记录，不新增审计系统。

```json
{
  "evidence": [
    {"id": "interaction_policy", "kind": "interaction_policy", "facts": "<校验后的业务策略或明确failure>"}
  ],
  "allowed_next_steps": [
    {
      "id": "entry:human_support",
      "actor": "user",
      "stage": "request_entry",
      "surface": "mall_chat",
      "requires_user_confirmation": true,
      "permitted_effect": "open_entry",
      "evidence_ids": ["interaction_policy"]
    }
  ]
}
```

上例只展示新增部分，不覆盖现有request、tool、policy、capability、execution证据。策略接口成功时即使其入口不在RoutePlan内，也保留为交互证据；不能被现有“仅接纳计划内能力”过滤掉。

规则必须通用，不匹配ISO06原句、商品名、价格或入口ID执行特例：

| 表达类别 | 允许依据 | 不允许的推导 |
|---|---|---|
| 已查到的事实 | 本轮有效工具／政策证据 | 将一次查询成功说成已登记未来服务 |
| 条件查询建议 | 已注册只读路径及已确认支持／本轮成功读取，沿用现有必填参数定义 | 要求提供订单号不等于已核验，也不能替未知查询保证结果 |
| 用户入口建议 | 校验后的入口策略，按actor、surface、确认及effect表达 | 入口开放不等于工作人员已接手 |
| 助手已执行 | 对应对象、动作、时点的可信回执 | 用户历史说法、路由计划、入口卡不是回执 |
| 已安排未来处理 | 真实任务／受理记录与能力证据 | 有能力、有页面或一句“我会”不构成安排 |
| 未知／失败 | 对应缺口及其来源 | 缺材料不能说业务不支持，不能凭空添加替代服务 |

`allowed_next_steps`由代码从上述来源组装，不接受模型自报的列表。实现只需覆盖现有入口与受控只读建议，不预建未来通知、维修或真实人工系统。列表约束的是客服可以承诺提供的步骤；不是强制回复全部列项，也不是禁止普通解释或不承诺服务的用户自行操作建议。

生成与judge必须拿到同一份脱敏后的证据和步骤，内部记录能够还原其来源。不要修改`generation_evidence_complete`的既有含义：它表示生成来源是否共享，不表示所有业务事实已齐全。不得把模型候选反向补进facts。

## 6. Prompt与judge语义契约

修改现有`tool_usage.md`、`final_answer_style.md`、`answer_judge.md`及对应registry版本；禁止新增“看到转人工就拦”的规则。

### 6.1 生成必须遵守

1. 保留故障后的澄清／人工出口；只有澄清能帮助解决缺口时才追问，入口建议按当前策略中的用户主体和阶段表达。
2. 先完整回答已知内容，再准确说明对应未知；没有有依据的下一步时允许结束，不强行编造安抚性动作。
3. 允许“您可以在商城客服对话中要求转人工”；不扩大成留资、代提交、等待回电或已经转接。例句是语义示意，不是必须逐字匹配的验收模板。
4. “可办理”“条件满足后可查询”“已经办理”“已经安排后续处理”使用不同依据，不以“尚未执行”一律拒绝合法条件建议。
5. 不输出策略字段、入口ID、调试信息。保留ISO03宽松标准：通用咨询不强制逐项复述所有政策条件。

### 6.2 judge继续使用现有三个维度

- `omission`：检查明确诉求与决定答案的边界；不因未列全用券条件，或没有强行推荐人工而判漏答。
- `conflict`：对照同一对象、阶段、主体和范围。仅有入口却说真人已接手可判冲突；入口证据缺失本身不能证明入口不存在。
- `unperformed`：覆盖无依据的已做、即时代办及未来办理承诺，不限“持续”任务。ISO06整句“留下联系方式，我帮您转人工进一步确认”暗示助手留资代办，超出open_entry，应判fail；合法用户入口引导、否定、假设、用户自行操作和有依据的条件查询应pass。

`fail`必须指出实际原句与有效证据ID，不能仅凭关键词；确认生成来源完整却无代办依据，与评测漏采材料要区分，后者用uncertain。新`interaction_policy`证据必须能通过现有引用ID解析；不放宽其他枚举、类型、原句引用、pass可省requirement或失败证据约束。

不要要求模型从缺失材料中猜“人工不支持”。当前策略的open_entry范围本身即可证明候选越过入口阶段，无需把human_takeover添加到本轮业务计划。

## 7. 出口、备用稿与模式

| 模式 | 本次要求 |
|---|---|
| off | 不新增judge或交互策略请求，保留原出口；通用Prompt文本会随版本修订，不能宣称输出逐字不变 |
| shadow | 新策略仅供评审记录；维持现有生成payload和旧出口，generation_evidence_complete=false；不得把旁路判定当成新生成已受约束 |
| enforce | 相同新快照供生成、judge、受控备用稿；有hard issue、fail、uncertain或judge错误时复用现有完整互斥降级 |

本期修复的完整效果验收针对eligible的enforce路径，不把off／shadow说成已修复，也不自动修改日常模式。生成／judge次数不增加，judge截止及无重试不变；新增策略查询是独立至多一次的业务GET。

备用稿必须保留199元／无库存等已知事实与提醒查询失败边界；若策略有效，可依据相同策略组织可选用户入口指引；策略失败则不加入未确认的入口。不要强制每次附带人工入口，也不要让judge故障变成“业务故障”。未知说明要点名相应事项，不能覆盖已查询成功的商品事实。

不在被拒候选后追加纠正，不正则删句，不再调用模型重写。备用稿不得使用原错误候选，也不能将“打开入口”显示为“已接手”。既有ISO08政策备用稿问题BC-029仍单列；本次不顺手重写整个RAG，但不得增加教学片段进入正文。

不因普通入口建议把`next_action`改成真实执行或新建Workflow；用户要求人工后的现有Java卡片路径不改变。不得把`transfer_to_human`统一解释成真人成功，该枚举还涉及现有审批等路径。

以下用例在本合同中事前规定；正反例成对，固定替身验证结构，真实judge评测验证语义，不能混计。

| 编号 | 输入／初始条件与候选 | 必须观察 |
