## 1. 产品目标与当前问题

**先确定客户问的是哪件商品，再查询该商品的实时价格、库存和活动信息。** 明确对象时直接回答；无法唯一确定时才澄清。

当前代码有四个缺口：完整商品名被缩成类别词；搜索多结果默认取第一款；已传入的页面商品编号没有用于精准查询；会话只保存最近商品名，缺少编号与候选选择绑定。

例如，“轻量露营折叠椅多少钱？”经过现有 `product_query_keyword` 得到“折叠椅”。`search_products` 又以 `products[0]` 生成摘要。因此，意图识别正确也可能回答另一款。

以上依据是当前源码及上一轮局部函数核验，不是新一轮真实模型对话成绩。历史两款帐篷隔离复现见[DESIGN-001](../../03-评测与问题/项目评测记录.md#design-0012026-10-07-三份材料与源码设计核验)。

## 2. 首版范围与设计决定

1. 保留 `product_query` 意图，不新增意图标签、Agent、模型或商品业务接口。
2. 复用 Java 现有商品搜索、按编号详情 GET，以及现有模型调用。定位对象不另加一轮模型调用。
3. 先覆盖详情页指向、完整商品名、多结果澄清、候选选择、最近明确选定商品的简单追问。
4. 选择列表先用编号文字展示，不新增商品选择卡片。每次最多展示 3 款；数量更多时说明还有其他匹配，提示补充名称或款式。3 是本次 MVP 展示上限，不是推荐排序规则。
5. 只查询商品信息；不加入购物车、不创建订单、不支付，也不准备、取消或提交售后申请。

不扩展推荐排序、商品比较、多商品同时问价、复杂指代如“刚才最便宜的那个”、跨会话记忆、规格选择或 SKU 模型。业务对象仍是项目现有商品编号。上述表达不能被强行解释为第一款；可以请客户明确名称或拆开询问。

查询失败不得报旧价格或猜库存。本轮只补定位所必需的“查询成功／失败”边界，完整故障反馈、重试和部分结果策略留给下一项。

## 3. 商品指向规则

所有规则以客户原句为输入。商城已通过 `runtime_context.userMessage` 保留原句，不从拼接的页面说明中提取客户主动选择。

| 编号 | 客户表达或条件 | 应采用的对象 | 不允许的行为 |
|---|---|---|---|
| R1 | 明确商品名称，如“轻量露营折叠椅” | 按完整名称搜索、核对 | 丢掉“轻量”等区别；被页面或历史商品覆盖 |
| R2 | 明确商品编号，或本会话有效候选选择 | 核验该编号；选择按候选快照映射 | 模型编造编号；按数据库列表当前顺序解析 |
| R3 | “这件／这款”，且有有效商品咨询入口上下文 | 已校验的 `relatedProductId` | 把文本中任意数字当页面编号 |
| R4 | “刚才那款／刚才这款” | 本会话最近成功查询并明确选定的商品编号 | 选搜索列表第一款；凭压缩聊天记录猜对象 |
| R5 | “这件／这款”无页面关联，但本会话有唯一已选商品且无未决多选 | 使用该唯一商品编号 | 有待选候选时跳回旧商品 |
| R6 | 明确新名称或“换看……” | 重新定位新对象，替换旧商品候选 | 旧候选或旧商品覆盖新诉求 |
| R7 | 没有可用对象、未决多选、或两种指向无法同时成立 | 询问名称或列候选 | 默认选第一款或套用订单选择规则 |

“这件”与“刚才那款”分别解析，不统一使用“页面永远优先”的规则。页面是椅子、客户明确说“我要问野餐垫”时，直接按野餐垫查询，无需再问是否切换。

“这件”指的是请求中关联的咨询入口商品。现有前端只有点击“咨询这件商品”才更新 `csContext`，不是每次页面导航都自动更新。因此，本轮不承诺客服能感知用户当前屏幕；点击另一商品的咨询入口后，使用新关联商品。

如果原句同时明确指定两个不同对象，又无法判断是在切换还是在比较，先请客户说明问哪件。不要通过新增大量关键词规则覆盖所有自然语言表达。

### 3.1 搜索结果怎样转成确定对象

查询成功后，按以下顺序处理：

1. 检查是否有唯一完整名称匹配。比较可忽略首尾空格及无意义标点，不能删除款式、容量等商品区别。“露营折叠椅”与“轻量露营折叠椅”不能归为同名。
2. 没有完整名称匹配，但只返回一个可信商品，且符合客户已明确的款式约束，可以选定该商品。
3. 返回多款且无法唯一核对时，展示候选，不生成第一款的价格、库存摘要。
4. 正常零匹配时说明未找到，请客户补充名称；查询失败时说明暂时无法查询。两种结果都不能回落到页面、历史商品或镜像来回答另一款。

“露营椅”等类别别名可以规范成“折叠椅”，但“轻量露营折叠椅”必须保留款式区别。如果完整名称无匹配，不自动删掉区别后选择一个近似商品。

## 4. 候选选择与连续对话

候选文案示例：

> 找到多款折叠椅，请选要咨询的款式：
> 1. 露营折叠椅
> 2. 轻量露营折叠椅
> 回复“第一款”或“第二款”；也可以补充完整商品名。

示例使用项目已有商品名称，不代表当前商品数量、价格或库存。

- 候选必须包含编号和名称，并与用户实际看到的顺序一致；后续按该快照解析，不重新搜索再取第二项。
- 首版支持“第一款／第二款／第三款”和“第1款／第2款／第3款”。纯数字、订单的“第二笔”以及复杂描述不作为商品序号自动执行。
- 只有商品任务正在等待选择时，这类纯选择答复才续接 `product_query`。即使模型把“第二款”判成闲聊，代码仍可按有效商品待选状态纠正；没有有效候选时询问对象，不能制造一次选择。
- 序号越界时重述现有候选，不使用页面或旧商品兜底。
- 新商品查询替换旧候选；客户选择后清空待选列表，成功读详情后保存新商品编号。
- 等待选择期间插入明确订单／售后等其他业务时，仍按本句处理，不强制拉回商品；旧商品候选失效，避免回来时误选。不得因此清理订单或售后上下文。
- 商品待选状态与退款 `open_task`、资格 `eligibility_query` 分开保存，不共享订单的 `pending_slot=order_id`。
- “好的／知道了”不等于选第一款；“先不看了”只结束商品待选，不取消退款。
- 对象已选定后，库存、价格、活动追问仍重新读取实时详情。记忆只保存对象和必要问句，不保存旧查询结论作为当前事实。
- 补“第二款”时还要保留原来问的是价格、库存还是活动，不能把这一轮当成没有问题内容的新商品搜索。

会话隔离沿用现有用户与会话校验。新会话或进程重启后的未知对象重新询问，不新增持久化或跨会话恢复。

## 5. 大模型与代码的职责

**模型理解表达，代码确认商品编号，业务接口提供实时事实。**

| 环节 | 模型可以做什么 | 代码必须保证什么 |
|---|---|---|
| 意图路由 | 判断本句是否商品咨询 | 保留现有标签；纯候选选择只绑定有效商品任务 |
| 搜索词 | 提取完整商品名称或类别，保留客户限定词 | 检查与原句一致，不让模型把轻量款改成普通款 |
| 页面与候选指向 | 使用提供的对象说明理解表达 | 编号只能来自受控页面、真实候选或经接口核验的明确编号 |
| 工具调用 | 在既有白名单内调用商品工具 | 受控编号与模型参数不一致时拒绝，不按模型新编号查另一款 |
| 最终回答 | 对已核实事实作简短说明，补已有通用活动规则 | 未确定对象只澄清；点名商品；价格、库存、活动都属于同一编号 |

现有 `product_route_plan_mismatch` 只比较规范后的类别词。修改后不能继续以“都含折叠椅”为理由允许换款，也不能为了支持完整名称直接删除参数校验。

已确定编号的页面咨询、候选选择及简单追问可以由代码直接读取详情，不必再让模型猜工具参数。需要提取名称时复用现有工具模型；模型不可用时，代码能可靠解析的明确对象照常处理，不能可靠解析就询问。不要为每种失败再调用一次语义模型。

未定对象的候选文案、查询失败文案由代码生成，避免最终回答模型自行选款。单商品事实问答优先复用确定性摘要；如仍用现有最终回答模型，只传已核实单商品事实并约束不得换款。涉及活动规则时保留 Tool＋RAG 的既有边界：通用规则不能证明某款能叠加优惠或最终到手价。

## 6. 实现契约与最小结构

本节字段是建议命名，可匹配现有风格调整，但以下行为必须一致。

### 6.1 业务数据与工具

- 搜索：继续使用 `/api/products?keyword=...`，取得含 `id`、`name` 的真实候选。
- 详情：复用 `/api/products/{id}`，读取同一个商品的价格、库存、活动和在售状态。
- 保留公开工具名 `search_products`；必要时给它增加可选 `product_id`，由内部函数区分搜索与按编号读取，避免新建一整套公开工具目录。
- 传明确编号时不能再按关键词搜另一款。候选选择完成后也按编号读取详情，以验证对象仍存在及事实仍有效。
- 商品不存在时说明该对象无法查询，不改查其他商品。已下架时如实说明状态，不宣称可购买；库存 0 与商品不存在、查询失败分别处理。
- `ToolCallTrace` 已支持 `candidates`、`clarification_field`、`clarification_prompt`，优先复用。多结果使用 `next_action=ask_clarification`，字段为 `product_id`；不能把“查询成功但待选对象”当成工具故障。
- 若商品客户端目前把异常与空列表合并，做最少调整保留成功／失败区别。日常商城不得用固定演示镜像证明当前商品事实；既有离线演练模式可以保留并标明来源。

### 6.2 会话与可观察信息

建议在现有 Python 会话记忆中增加独立 `product_query` 状态，最少保存：

| 信息 | 用途 |
|---|---|
| 已明确商品编号、名称 | 最近一款的简单追问；只在有效详情成功返回后更新 |
| 待选槽位、已展示候选编号和名称 | 精确绑定序号；不保留未展示的隐含候选供选择 |
| 原始商品问句 | 选择后继续回答原价格／库存／活动问题 |

不复制一份到 Java 会话，不建设统一任务引擎。Python 服务丢失商品状态时如实询问；Java 原有售后状态保持原样。

现有 `last_product_name` 若仍被观察页面或其他调用使用，可保留兼容，但不能据此唯一定位。不要把商品澄清写进通用退款 `open_task`，也不要让商品答案清掉原售后待办。

在既有 Trace／`session_state` 中记录最终商品编号、来源（明确名称／页面／候选／最近商品）、已展示候选及查询成功／失败。模型原始路由与最终纠正结果继续分别保留。无需新增独立日志系统；工具参数、摘要和会话状态中的编号应一致。

### 6.3 商城网关与旧退款卡

这是本次必须处理的相邻边界：现有 Java 在收到 Agent 回复后，仍可能先执行 `refundFollowup`，`sanitizeChatResponse` 也可能重发旧待确认卡。前端遇到一般非确认回复还会清掉活动凭证。

- Agent 明确返回商品咨询时，网关应先返回商品结果，跳过该轮旧退款续接和草稿准备。复用单次路由结果，不另建 Java 语义分类器。
- 商品咨询、候选澄清及该任务的读取失败都不修改旧退款订单、原因、版本、凭证、取消待确认状态或资格查询上下文，不重发旧卡。
- 商城响应可使用一个 `PRODUCT_QUERY` 标记表明本轮为只读商品咨询。它只是响应标记，不是新增意图，也不写入 Java 退款 `pendingAction` 状态。
- 前端沿用资格咨询保留旧确认卡活动凭证的做法，商品响应同样保留；旧卡仍可点击，但不因查询商品生成新卡。没有旧卡时也不会凭空出现确认卡。
- 客户随后明确回到退款、主动取消或点击原卡时，继续执行已有规则和有效期校验。商品候选选择不能被当成退款订单或退款原因。

## 7. 修改位置与实施顺序

| 顺序 | 位置 | 必须达到的结果 |
|---|---|---|
| 1 | `backend/agent/ecommerce_client.py`、`tools/tool_runtime.py` | 保留完整名称；搜索返回候选，按编号读详情；移除默认首项摘要；成功与失败不混淆 |
| 2 | `backend/agent/context.py`、`customer_service_agent.py` | 独立商品状态与解析；续接候选及原问句；只在唯一有效对象上回答；隔离售后任务 |
| 3 | `tools/langchain_runtime.py`、相关 Prompt | 模型路径与代码兜底复用绑定规则；参数校验覆盖商品编号和款式区别 |
| 4 | Java `CustomerServiceGatewayService.java`、前端 `shop/App.tsx` | 商品结果提前返回，旧退款卡及草稿保持有效；复用已有页面上下文 |
| 5 | `backend/tests/`、少量隔离接口／页面检查 | 按下一节验收并保存证据；通过即停止 |

需要同步检查 `hooks.py` 的必填参数校验：若商品工具支持按编号调用，不能仍只检查 `keyword`。同步检查 `tools/planning.py` 的工具白名单、`mcp_catalog.py` 的描述和现有商品工具调用点；没有新增公开工具时不要无理由改目录或标签。

`api/schemas.py` 已有商品意图与澄清结构，优先复用。Java `ProductController`、`ProductService` 已有搜索和详情接口，原则上不修改。前端只做旧卡活动凭证的必要调整，不新增 UI 模块。

实施 Agent 开始前再确认工作区现状，保留已有未提交修改；先检查商品工具所有调用点，再修改共同逻辑。不能只修无模型兜底，遗漏 LangChain 工具执行路径。

## 8. 定向验收与停止条件

使用两款同类商品 A、B，名称有区别，价格、库存明显不同；例如普通款与轻量款。数值由隔离样本确定，不能把历史初始化数值写成当前日常库事实。

验收只做以下 8 组关键链路，不以新增全量评测、模型对比或分数校准为前置条件。

| 编号 | 输入／条件 | 必须观察到的结果 |
|---|---|---|
| P01 | 从 B 的详情页咨询“这件多少钱，还有货吗？” | 最终编号为 B；价格、库存、名称都来自 B；不搜索并默选 A |
| P02 | 页面为 A，明确问 B 的完整名称；搜索同时含 A、B | 唯一完整名称绑定 B，保留区别；不多问一次是否切换 |
| P03 | 类别查询匹配 A、B，再说“第二款” | 首轮列两款不默选；次轮按展示顺序绑定 B，并回答原问题；无模型和固定模型故意误判序号两种路径都成立 |
| P04 | 候选显示两款后说“第三款”；或新会话直接说“第二款” | 不查询 A／B 来兜底；说明无有效选择并澄清 |
| P05 | 选定 B 后修改隔离库存，再问“刚才那款还有货吗？” | 编号仍为 B，读到新库存；新会话无历史对象时询问名称 |
| P06 | A、B 候选后改问商品 C，再回复旧“第二款”；含“好的” | C 替换旧候选，旧序号不复活；“好的”不自动选第一款 |
| P07 | 查询零匹配、读取失败、已选编号删除或下架 | 不默选其他款；无匹配与读取失败记录不同；没有无依据的价格库存或可购买承诺 |
| P08 | 已有退款草稿／确认卡时，查商品并选择候选，然后回到退款 | 商品回复不续接或重发退款卡；草稿、版本和凭证不变，历史卡保留活动状态；明确回到退款后原流程仍可续办 |

通过标准看实际商品编号和接口结果，不能只看 `intent=product_query`。适用的参数不一致检查需证明：受控对象是 B、模型想查 A 时，不能执行对 A 的查询或回答 A。

验证采用：少量 Python 定向检查＋既有模型替身工具检查；商城网关与前端改动用隔离接口及必要页面链路核验。至少截图保留“多款澄清→选择后回答”和“已有退款卡→商品咨询后旧卡仍有效”两条页面链路；每次消息／按钮操作后截图，沿用已有记录格式。不用对全部 8 组逐一重复浏览器测试。

覆盖调用契约和对象规则的检查通过后停止。受影响的既有关键词测试可以更新，但不能只把错误首项结果改成新预期：必须增加完整款名不丢失、序号绑定等实际行为断言。保留仍应成立的“露营椅→折叠椅”类别别名能力。

本规划不是新的在线模型调用或部署授权。实现后的证据分别标注代码检查、隔离模型替身、真实模型、用户手测，不能混记通过数量。真实模型对话如需开展，应另明确少量输入及边界；不得借验收提交、审批或退款。
