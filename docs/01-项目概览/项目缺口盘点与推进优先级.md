# 项目缺口盘点与推进优先级

整理日期：2026-10-11。进度续记到 2026-10-12。

本文用于整体把握缺口和推进取舍，各项进度以更新记录为准。当前运行与验收停点仍以 [项目交接](项目交接.md) 为准，具体问题和历史证据保留在 [BadCase](../03-评测与问题/问题台账.md) 与 [项目评测记录](../03-评测与问题/项目评测记录.md)。这里不另写一份当前停点。

## 一、已确认的推进重点

**接下来着重解决四个高优先级问题，按以下顺序推进：**

**只读资格咨询 → 商品对象定位 → 工具故障反馈 → 不支持业务的清晰出口。**

2026-10-12：前三项都已有约定范围内的实现记录。资格咨询已收尾；商品对象定位两条手测为用户反馈通过（MANUAL-003）；工具故障反馈已加载日常服务。第 4 项占位入口已加载日常服务，文案修订后的三条日常对话见 HUMAN-ENTRY-002，仍未接真人。运行停点只看项目交接。

本轮取消／保留流程按已验证范围阶段性收尾，不继续追求覆盖所有表达，不把更多模型对比、分数校准和全面评测作为推进这四项的前置条件。

| 顺序 | 高优先级问题 | 用户价值 | 首版处理范围 |
|---|---|---|---|
| 1 | 只读资格咨询 | 客户先判断这笔订单能否退款／退货，再决定是否办理 | 读取本人订单和资格事实，说明结果及原因；咨询不创建办理草稿、确认卡或售后申请 |
| 2 | 商品对象定位 | 回答的是客户指向的商品，避免混淆不同商品的价格和库存 | 优先处理明确商品及多结果澄清，不默认取第一款；不扩展完整推荐系统 |
| 3 | 工具故障反馈 | 客户知道应该换查询条件还是稍后重试 | 区分正常无匹配和查询失败；已知事实可答，未知价格／库存不猜测 |
| 4 | 不支持业务的清晰出口 | 客户清楚系统能做什么、下一步怎么处理 | 保留换货、质量售后等真实诉求，明确支持范围及可核实的处理途径；不改写成退款或无理由退货 |

### 1. 只读资格咨询

2026-10-11进度：代码已实现并通过定向隔离验证，日常本地服务已加载且加载前后8张MySQL业务表未变。用户随后手测反馈「没问题」，按当前MVP范围收尾，不再追加评测；下一项是商品对象定位。手测反馈与自动验证证据分别记录，助手未追加真实模型复测。见[产品Plan](../02-产品设计/04-只读资格咨询/只读资格咨询产品设计计划.md)和[实现记录](../../analysis/04-只读资格咨询/只读资格咨询实现验收/结果.md)。下方缺口描述保留为改动前背景，不再当作编码待办。

- **典型输入：**「这笔订单还能退吗？先别申请。」
- **当前缺口：** 通用政策咨询与办理已有独立路径，但具体订单的只读资格查询尚未完整接通。不能用通用政策代替这笔订单的实际资格，也不能因为查询资格就准备申请。
- **最小做法：** 复用已有订单读取与资格规则，返回能否办理、具体原因和缺失事实；客户明确提出办理后，再进入现有申请流程。无需为此重建售后状态机。
- **收尾标准：** 本人订单可查；不符合条件或事实不足时准确说明；咨询过程没有办理或提交副作用。

### 2. 商品对象定位

2026-10-12进度：用户先在另一位Agent修改商品代码期间并行推进故障反馈规划，随后明确要求本聊天读取Claude Code最新会话并接续11:51中断点。现已完成必要补充修复及定向隔离验证：Python43/43、接口／页面15/15、6轮截图，未调用在线模型、未提交或退款。随后已按用户授权加载日常Java／Python及页面，加载前后8张MySQL业务表未变，两条[用户手测](../03-评测与问题/商品对象定位手测清单.md)待反馈；见[实现与接续记录](../../analysis/05-商品对象定位/商品对象定位实现验收/结果.md)及[产品需求规划](../02-产品设计/05-商品对象定位/商品对象定位产品需求规划.md)。下方缺口描述保留为设计前背景，不再当作尚未开始的编码待办。

- **典型输入：**「这款帐篷多少钱？」「刚才那款还有库存吗？」
- **当前缺口：** 当前商品工具存在多结果取第一款生成摘要的路径；页面商品、文本指向及连续指代尚未形成完整规则。这是代码可见风险，不代表所有商品问答都已发生错误。
- **最小做法：** 能明确定位就查询该商品；多款匹配时列出少量候选，先确定对象；客户表达与页面对象冲突时澄清。
- **收尾标准：** 两款商品不混价；模糊查询不默选第一款。先覆盖明确对象和多结果澄清，不为了覆盖所有「它／那款」表达扩大实现。

### 3. 工具故障反馈

2026-10-12进度：代码已实现，并按规划第8节通过定向验收。同日已加载日常服务，8 张 MySQL 业务表和商品价格库存未变，没有注入故障，也没有发送对话。证据见 [FAULT-001](../03-评测与问题/项目评测记录.md#fault-0012026-10-12-工具故障反馈定向验收)、[实现记录](../../analysis/06-工具故障反馈/工具故障反馈实现验收/结果.md) 和 [加载记录](../../analysis/06-工具故障反馈/工具故障反馈实现验收/加载本地服务/结果.md)。下方缺口描述保留为改动前背景，不再当作编码待办。

- **典型输入：**「查一下折叠椅的价格和库存。」
- **当前缺口：** 商品查询的正常空结果与异常可能都返回空列表，下游按同一类未找到商品处理；客户和记录难以区分没有商品还是服务故障。
- **最小做法：** 保留查询是否成功和业务结果的区别。正常无匹配提示调整条件，查询失败提示稍后重试；部分字段可核实时只回答已知部分。
- **收尾标准：** 无匹配与服务失败的回复不同；失败不说成缺货，不生成无依据的价格／库存，记录与回复一致。

### 4. 不支持业务的清晰出口

2026-10-12后续进度：用户要求先放人工确认卡与开发中页面。商城代码已实现，50项隔离检查／25轮截图通过；明确改办时旧未提交卡失效，普通咨询保留草稿，正常退款／退货不受影响。同日文案修订后已加载日常服务（镜像 `sha256:b2928f7506e9`），回复和确认卡不提开发中，说明页仍提示开发中，见 [HUMAN-ENTRY-002](../03-评测与问题/项目评测记录.md#human-entry-0022026-10-12-人工入口文案修订日常加载与对话验证)。未接真人。见[规划](../02-产品设计/07-不支持业务与人工入口/不支持业务清晰出口产品需求规划.md)与[验收](../../analysis/07-不支持业务与人工入口/人工客服占位入口实现验收/结果.md)。Python独立工作台未接此入口。

- **典型输入：**「收到时就破了，我只要换一件，不要退款。」
- **当前缺口：** 换货及部分质量售后没有完整办理能力。意图清楚但暂不支持，与不知道客户想做什么是两种情况，不能反复澄清或替客户改成退款。
- **最小做法：** 准确复述客户诉求，说明当前支持范围，给出现有且能核实的人工处理途径。没有真正的坐席接管时，不回复「已转人工」「已受理」。
- **收尾标准：** 换货诉求不误入退款／无理由退货，不产生申请；下一步说明清楚，不虚报处理状态。

## 二、其他缺口及暂缓事项

以下事项保留在清单中，不作为上述四项的前置条件。

| 事项 | 当前边界或影响 | 推进取舍 |
|---|---|---|
| 完整换货与质量售后流程 | 当前没有完整办理链路；「明确出口」不等于支持换货 | 先完成第4项的清晰出口，完整流程暂缓 |
| 真人客服承接 | 系统有联系人工的回复或动作标记，但尚未核实真正的坐席接管、排队和对话交接 | 有实际运营需求后再接通，当前如实说明范围 |
| 订单级退货运费来源 | 无法核实具体订单由谁承担退货运费，条件不能靠模型猜测 | 等业务数据来源明确后再做 |
| 跨办理任务的复合请求 | 如「取消A的退款，再准备B的退款」，顺序、依赖及失败恢复没有完整闭环 | 单项任务优先，复合任务暂缓 |
| 中断后恢复办理 | 未提交草稿驻留进程内，服务重启后需重新核对；已提交申请保存在业务数据库 | 本地演示可接受，持续使用时再做 |
| 回答依据与未知信息展示 | 客户不易区分订单事实、通用政策和未核实信息；现有事实约束不等于所有最终回复均已逐项验证 | 中期补简洁依据／待核实提示，不立即建设复杂引用系统 |
| 自动取消的可靠性 | BC-013仍开放，高分仍可能判错，分数未经校准 | 保留风险记录与默认关闭，不继续扩大当前评测 |
| 退货收件信息文案 | 「退货联系人」容易被误解为客户寄件人，实际填写商家收件信息 | 操作出现困惑时做小文案改动，暂不扩展地址管理功能 |

## 三、维护工作：避免重复修复和评测误报

### 旧评测判定器误报（BC-002）

历史离线回归的部分回答已表达业务边界，却因标点归一化和同义表述匹配被判失败。这是评测判定与文案契约问题，不能直接写成Agent不懂业务。

等需要使用这套评测支持决策时，再修对应判定；不为了把历史通过数改成满分而排进当前主线。

### 交接记录与源码状态不一致

旧交接将BC-001/004列为未修复，但本次盘点时当前Python源码已包含最新事实缺失时阻断、可信审核身份校验及终态防重逻辑。也已看到支付状态必须明确为PAID的资格校验。

因此这些旧条目先列为**文档、实现和验收证据待对齐**，不能直接安排重复修复，也不能仅凭静态阅读宣称最新运行验收已经完成。商城业务链路与Python模拟工作台仍须区分。

## 四、明确不纳入近期范围的能力

以下是首版范围取舍，不是必须补齐的漏洞：

- 部分退款／部分退货。
- 退货后库存恢复与重新上架判定。
- 图片凭证上传。
- 外部支付渠道退款。
- 真实物流平台接入与物流拦截。

## 五、推进与验收原则

1. **一次处理一个高优先级问题。** 先明确用户可见行为和最小范围，复用已有能力，不顺带建设新框架或重构标签体系。
2. **默认只验一条正常流程和一条直接相关的失败路径。** 涉及身份、归属、提交或资金时，再补对应关键边界；不省掉必要校验，也不自动扩大到全量评测。
3. **相关检查通过就收尾。** 只有新改动、失败或未解决的直接问题才触发复测；不以覆盖所有表达为目标。
4. **实际对话保留文字记录和逐轮截图。** 回复、按钮和真实状态分别记录，不把模型标签正确当成办理成功。
5. **明确完成边界。** 固定模型检查、真实页面结果、静态源码判断与未验证事项分开记录；未纳入首版的能力不算本次失败。
