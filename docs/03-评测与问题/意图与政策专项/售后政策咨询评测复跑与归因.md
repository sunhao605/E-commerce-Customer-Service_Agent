## 判断

**两条用例都复现了失败，业务行为通过 0/2。** B01 问退款政策却收到发票说明；B02 明确只是咨询，却被要求补订单号，并保存了退货办理待办。两条 HTTP 都是 200，意图模型都实际调用成功，不能把 HTTP 成功当成任务完成。

B01、B02 共有的产品缺口是：稳定政策的只读咨询没有接到正确业务路径。当前 `faq_query` 的语义与实现主要限定发票，见 [Prompt 第 8 行](../../../backend/resources/prompts/route_contract.md#L8)；模型把 B01 分进 FAQ 后也无法获得退款知识。B02 则在更前面的分流已经偏离。

### B01 为什么会被分到 FAQ，而它明明不是发票问题

用户追问：“退款政策是什么？我先了解一下，不申请退款，为什么会路由到 faq_query，这明显不是发票问题呀。”这个输入确实没有发票诉求；不能把本次 `faq_query` 写成已正确识别并支持的售后咨询。

已确认的事实是：意图模型报告了 `faq_query`，无故障回退；[路由解析](../../../backend/agent/models/router_client.py#L59) 校验标签是否在允许集合内，并没有检查本句是否符合发票主题，随后执行固定发票分支。当前 Prompt 只列“发票开具时间、发票下载等稳定 FAQ”，没有清晰规定售后政策咨询应该走哪条路径。`faq_query` 的名称本身比实际发票实现宽，路由契约与支持范围不够清楚。

一种解释假设是：模型把“只了解退款政策、不申请”理解成一般规则问答，选择了名称最接近通用 FAQ 的标签。没有采集模型内部选择理由，不能把这个解释当作模型实际思考过程。B01 应同时记录**路由契约的咨询入口缺口**与**FAQ 分支固定发票的承接问题**；后者是发票答案的直接代码原因，不意味着前者已经判对。下文“复用 FAQ”是扩展其定义和实现的修正建议，不是宣称当前 FAQ 已支持退款咨询。

**政策内容的相邻缺口，仅静态确认：**[退货材料第 8 行](../../../backend/resources/knowledge/received_return_policy.md#L8) 仍要求用户提供明确原因，而 [商城提交](../../../ecommerce-backend/src/main/java/com/teachdemo/ecommerce/order/ShopService.java#L408) 已按“七天无理由退货”创建申请。修复时必须核对这份材料；它不是这次两个回复错误的直接来源，因为本轮没有读到该政策。

## 修正的最小方案

2026-10-10 后续官方资料评估更新：结合现有“模型仅返回一个意图、代码按标签选择路径”的结构，当前优先建议改为新增 `refund_policy_query`、`return_policy_query` 两个只读标签，并明确发票 FAQ 的边界。下面保留此前扩展 FAQ 的方案供比较；它不是最新优先建议，两种方案都尚未实施。完整理由见 [意图标签评估](../../02-产品设计/02-意图与政策咨询/意图标签设置评估与调整建议.md#判断)。

**首版复用 `faq_query` 承接只读售后政策咨询，按主题使用现有政策对象。** 项目已有 `KnowledgePathResult`、`REFUND_POLICY`、`RETURN_POLICY`、`INVOICE_FAQ`，可复用 [knowledge.py](../../../backend/retrieval/knowledge.py#L13)；不需要增加模型调用或重做售后流程。

| 改动位置 | 最小改动及必要边界 |
|---|---|
| `route_contract.md`；`planning.py:classify_intent` | 明确“了解退款/退货条件、政策且没有提出办理”走 `faq_query`，明确申请仍走原办理标签。同步模型故障时的规则兜底；保持合法模型标签直接采用，不恢复关键词覆盖模型结果 |
| `customer_service_agent.py` 的 FAQ 分支；`knowledge.py` | FAQ 分支接收本句，按发票、未发货退款、签收退货主题选择现有对应政策，并返回匹配回复和引用。售后咨询直接使用核对过的政策对象，发票保留现有路径；不调用订单工具，不建立售后 Workflow |
| FAQ 缓存读取与写入 | 发票缓存只在确认主题为发票时使用；当前 Agent 的写缓存条件也仅按 `intent==faq_query`，需同时收窄为发票主题。首版售后政策咨询不缓存生成答案，防止再次串题。见 [缓存写入](../../../backend/agent/customer_service_agent.py#L621) |
| 两份售后政策 Markdown | 与已确认的商城范围、客户/管理员职责和退款终态同步；无理由退货不要求另编原因，通用规则不冒充具体订单资格 |

不能只让 B02 的标签变成 FAQ：B01 已说明“分到 FAQ”仍会答错主题。也不能只改追问文案：B02 错误的办理待办还会影响下一轮。采用上述直接读取已有政策对象的首版，不需要走 [当前仅把 FAQ 映射为 invoice 的检索计划](../../../backend/retrieval/hybrid_retrieval.py#L108) 来检索售后政策；后续若改成统一检索，再按政策主题调整其范围。

修复后验收：相同 B01、B02 均回答匹配政策与依据；`next_action=answer_user`、`clarification=null`、工具 0、`workflow=null`、`open_task=null`；计划不要求业务工具或售后 Workflow。另补明确办理、咨询后改为申请、正常发票及缓存串题的相邻检查。商城入口需单独验收，不能继承 Python 的结论。本轮尚未运行这些修复后或相邻检查。
