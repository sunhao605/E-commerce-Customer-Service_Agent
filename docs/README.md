# 文档阅读导航

整理日期：2026-10-12。这个项目是电商客服与售后 Agent 演示原型，包含商城、管理后台和 Python 工作台。先了解客户与管理员的业务流程，再看 Agent 如何理解请求、读取事实和推进售后。

## 第一次看项目

| 顺序 | 要弄清的问题 | 阅读入口 |
|---|---|---|
| 1 | 这个项目做什么，系统如何分工 | [项目导读](01-项目概览/项目导读.md)；需要图解时看[用户旅程](01-项目概览/用户旅程/用户旅程流程图.md) |
| 2 | 目前做到哪里，还有哪些边界 | [项目交接](01-项目概览/项目交接.md) |
| 3 | 为什么做这些改进，如何安排优先级 | [项目缺口盘点与推进优先级](01-项目概览/项目缺口盘点与推进优先级.md) |
| 4 | 某项功能怎样设计 | [产品设计目录](02-产品设计/README.md) |
| 5 | 是否验证过，失败在哪里 | [评测与问题目录](03-评测与问题/README.md)，再沿证据链接进入 [analysis](../analysis/README.md) |

导读、设计与图示保留了各阶段的观察。**当前停点以项目交接为准；验收范围以项目评测记录及原始结果为准。** 设计预期、用户手测反馈和助手运行结果分别阅读。

## 后续文件怎么放

- 正式说明放在 `docs`；同主题的 Markdown 与 HTML 放在一起。HTML 是讲解版或设计时快照，更新状态先看正文和项目交接。
- 验收材料放在 `analysis` 对应主题下。一次运行的脚本、冻结样本、结果、日志、截图和源码快照放在同一目录；同一专项的多轮运行继续用子目录区分。
- `01–08` 是主题编号，沿用原缺口一至七的对应关系，`08` 为候选订单绑定；它们不表示已完成，也不代替推进优先级。`90` 与 `99` 放横向验证和参考材料。
- 新增主题或专项时更新所在目录的 README。新专项用具体名称，避免“本次验证”；需要区分多次启动时加日期。
- `.runtime`、`.before`、`before-fix`、初次失败记录等用于回溯，不作为新人阅读入口。原始结果里的历史路径和哈希保持原样，通过当前导航找到移动后的材料。

本次只整理路径、名称和引用，没有更新业务状态或新增业务验收成绩。目录整理的范围与检查结果见[整理记录](04-学习与复盘/文档目录整理记录.md)。
